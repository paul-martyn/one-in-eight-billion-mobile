# Стек для интеграции нового игрового UI

Рассмотрено 31 октября 2026. Это решение для следующего этапа и пояснение к `CLAUDE-INTEGRATION-PROMPT.txt`. Библиотеки в ходе этого обзора не устанавливались, текущая игра не подключалась. Установленный стек остаётся React 19.3.1, TypeScript 7.0.2, Vite 8.3.5.

## Решение

Сохраняем React + TypeScript + Vite. Для приложения, состоящего преимущественно из экранов, карточек, текста, панелей и жестов, этот стек позволяет сделать полноценный мобильный игровой интерфейс. Близость к будущей Unity-версии определяют экранный flow, композиция, ассеты и параметры движения. Сам выбор WebGL/Canvas вместо DOM не делает код автоматически переносимым в Unity.

| Слой | Выбор | Граница ответственности |
|---|---|---|
| Экраны | React + TypeScript, CSS и общие токены | Представление; без расчётов симуляции |
| Сборка | Vite SPA | Быстрая разработка и статическая сборка; SSR сейчас не требуется |
| Переходы и жесты | Motion for React — основной кандидат для новой работы | Вход/выход, панели, карточки, жесты, перестановки; CSS для простых состояний |
| Готовые сложные анимации | Сохранить GSAP, если на нём уже сделаны макеты Claude | Один владелец анимируемого свойства; не переписывать готовую хореографию без причины |
| Экранный flow | Отдельный типизированный контроллер; XState для вложенных/ветвящихся состояний | Экран, панель, возврат, переход, прерывание; не модель жизни персонажа |
| Состояние игры | Единственный экземпляр исходной симуляции за адаптером | Оригинальные правила, RNG, время и сохранение; UI получает read-only проекции |
| Проверки | Существующий Node harness + сравнение поведения, Playwright для браузера | Эквивалентность core отдельно от визуальной проверки |

Motion предоставляет React-компоненты, layout-анимации и распознавание жестов; это соответствует основной работе над экранами. [Официальная документация](https://motion.dev/docs/react). GSAP предлагает управляемые последовательности; его `useGSAP` интегрирует жизненный цикл и очистку с React. Поэтому существующие качественные GSAP-сцены разумно сохранить. [Руководство GSAP](https://gsap.com/resources/React/).

Окончательный выбор между Motion и уже используемым GSAP нужно сделать после инвентаризации экранов Claude. Не устанавливать обе библиотеки по умолчанию. Если нужны обе, закрепить границы и не управлять одним transform/opacity из двух систем.

XState описывает состояния и переходы через события. Для сложного игрового flow это полезная основа, но небольшому линейному набору экранов достаточно reducer и стека навигации. [Официальное описание](https://stately.ai/docs/state-machine-actors). При установке выбирать проверенный стабильный релиз и документацию соответствующей версии. Существующие работающие версии зависимостей не обновлять заодно с интеграцией core.

Дополнительный глобальный store не обязателен. Нельзя создавать второе изменяемое состояние персонажа в Zustand, React или XState. Для подписки на адаптер можно использовать стандартный механизм внешнего store React; отдельное хранилище UI добавляется при конкретной потребности. То же относится к роутеру: внутренний игровой экран и браузерный URL — разные задачи.

## Что подключать только по необходимости

- **Rive:** отдельные анимированные персонажи/иллюстрации при наличии подходящих `.riv`-ассетов. Сначала проверить один реальный ассет на Web и целевой Unity-платформе. [Официальный Unity runtime](https://github.com/rive-app/rive-unity) существует, но его README всё ещё обозначает technical preview; это не основание обещать бесшовный перенос всего UI.
- **PixiJS:** отдельная насыщенная 2D-сцена с большим количеством спрайтов/эффектов, если она действительно нужна макетам. [PixiJS](https://pixijs.com/8.x/guides/getting-started/intro) — 2D renderer с WebGL/WebGPU; он не нужен для каждой карточки и формы.
- **Worker:** только если профилирование выявит блокировку UI симуляцией. Сначала доказать сохранение порядка команд, RNG и времени, затем менять среду исполнения.
- **PWA, серверные аккаунты, платежи, новый backend:** отдельные задачи. Они не требуются для связывания локальной симуляции с экранами.

## Главное изменение архитектуры

Предыдущий этап намеренно остановлен на `fixtures → UI`. Следующий этап:

```text
действие пользователя → UI-flow → команда адаптера → исходный core
                                              ↓
экран ← read-only view model / события представления
```

`reference/original-0.8.98` остаётся неизменяемым эталоном. Для работы приложения выделяется отдельная производная версия core с воспроизводимым извлечением/обёртками. Отделение DOM, часов, хранилища и транспорта — техническая работа, которую надо проверить сравнением поведения. Сохранность SHA-256 эталона сама по себе не доказывает эквивалентность производного core.

Особенно важно разделить игровой RNG и декоративную случайность. Частицы, idle-анимации, повторный рендер и закрытие панели не должны менять исход жизни. Корректность команды не должна зависеть от завершения анимации; пропуск/прерывание движения оставляет тот же результат игры.

## Что готовить для Unity

Переносимые результаты: карта экранов и событий, сериализуемые команды и состояния, стабильные ID, сценарии воспроизведения, дизайн-токены, исходники изображений/шрифтов, motion-спецификация. Для каждого перехода фиксируются trigger, duration, delay, easing/spring, начальное/конечное положение, прерывание, пропуск и политика ввода. Система координат — локальная для портретного экрана, а не размеры окна desktop.

React, CSS, Motion/GSAP и XState не превращаются автоматически в Unity-код. В Unity предстоит реализовать отображение и проверить симуляцию. Например, собственные USS-переходы Unity имеют duration/easing/delay, но это отдельная система исполнения. [Документация Unity](https://docs.unity.com/en-us/engine/7000.0/manual/best-practice-guides/bpg-uiad-index/styling).

Самое полезное для будущего переноса сейчас — довести реальный игровой путь на новых экранах и записать проверяемую спецификацию его поведения, не заменяя оригинальные правила удобными для макетов приближениями.
